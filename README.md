# The Oracle

An interactive, physical, spoken oracle for CIID. A visitor places a hand
over a photoresistor, and the ritual begins: the oracle wakes, asks for a
name, matches it to a real CIID May 2026/27 student profile, listens to a
question, and speaks back an imaginative, unexpected possible future built
from fragments of that person's own background.

There is almost no interface. The physical gesture, the voice, the light,
and the AI's response *are* the interface.

```
IDLE → HAND DETECTED → AWAKEN → ASK NAME → LISTEN FOR NAME → IDENTIFY
     → ASK QUESTION → LISTEN FOR QUESTION → INTERPRET → GENERATE
     → REVEAL → RETURN TO IDLE
```

## Live static demo (GitHub Pages)

`docs/` is a separate, self-contained build with no backend at all — it's
what's published at GitHub Pages. GitHub Pages only serves static files, so
it can't run the Node server this project otherwise uses; the demo swaps
every server-dependent piece for a client-side equivalent:

- Profile loading + fuzzy name matching → `docs/js/profiles.js`, reading a
  bundled `docs/data/profiles.json` instead of hitting an API.
- Fortune generation → `docs/js/fortune.js`, the same offline generative
  template the full server falls back to (a static page should never ship
  an Anthropic API key to the browser, so it always uses this).
- The Arduino bridge → `docs/js/webserial.js`, using the **Web Serial API**
  to talk to the board directly from Chrome/Edge over HTTPS — no Node
  process required. It needs a user gesture, so it's wired to the dev
  panel's "Connect sensor" button rather than happening automatically.

Speech recognition/synthesis, the visualizer, and the ambient audio are
identical to the full app — those never touched the server to begin with.

## Quick start (full app — live AI + real Arduino)

```bash
npm install
npm start
```

Then open **http://localhost:4173** in Chrome (Web Speech API — speech
recognition and speech synthesis — currently works best there) on the
MacBook that has the microphone and speakers you want to use.

No Arduino? No API key? The experience still runs end-to-end:

- Press **``` `** (backtick) or click the small dot in the bottom-right
  corner to open the **developer panel**, and use **"Hand detected"** to
  start the ritual by hand instead of by sensor.
- Without `ANTHROPIC_API_KEY` set, fortunes are generated by a local
  offline generator instead of the live model — the ritual and pacing are
  identical, just with a simpler oracle "brain."

## What's real vs. simulated

| Piece | Real implementation | Fallback if unavailable |
|---|---|---|
| Hand trigger | Arduino + photoresistor over serial | Dev panel "Hand detected" button |
| Speech-to-text | Browser Web Speech API (mic) | Dev panel text inputs for name/question |
| Text-to-speech | ElevenLabs (human-sounding voice) | Browser Web Speech API, then captions on screen |
| CIID profiles | Scraped + cached at server startup | Bundled cache in `server/data/profiles.cache.json` |
| Fortune generation | Anthropic API (Claude) | Local generative template (`server/fortune.js`) |

## Setup

### 1. Install

```bash
npm install
```

`serialport` is an optional dependency for talking to the Arduino. If it
fails to build on your machine, the server still runs fine — it just logs
`serialport not installed — running in simulation mode` and you drive the
ritual from the dev panel instead.

### 2. (Optional) Add a live AI brain

```bash
cp .env.example .env
# then edit .env and set ANTHROPIC_API_KEY=sk-ant-...
```

`server/index.js` reads `ANTHROPIC_API_KEY` from the environment
(`npm start` auto-loads `.env` — see `server/index.js` if you'd rather
export it in your shell instead). Without a key, fortunes fall back to the
offline generator in `server/fortune.js`.

### 3. (Optional) Give it a real voice

The browser's built-in Web Speech voices are fine but noticeably synthetic.
For a genuinely human-sounding oracle, add an [ElevenLabs](https://elevenlabs.io)
API key to the same `.env`:

```bash
ELEVENLABS_API_KEY=sk_...
# ELEVENLABS_VOICE_ID=XrExE9yKIg1WjnnlVkGX   # optional — defaults to "Matilda"
```

`server/tts.js` synthesizes each line server-side and streams the audio back;
`public/js/speech.js` plays it if the call succeeds and falls back to the
browser voice for that line (and every line after, if the key is missing)
without ever breaking the ritual. To use a different voice, grab a voice ID
from your ElevenLabs Voice Library and set `ELEVENLABS_VOICE_ID`. The dev
panel's **Voice** status row shows which one is actually active.

This only applies to the full app — the static GitHub Pages build in `docs/`
has no server to call ElevenLabs from (and shouldn't ship an API key to a
static page), so it always uses the browser voice.

### 4. (Optional) Connect the Arduino

Wire a photoresistor as a voltage divider into `A0` (see comments in
`arduino/oracle_photoresistor/oracle_photoresistor.ino` for the exact
wiring), upload the sketch, and plug the board into the MacBook over USB.
The server auto-detects the first USB-serial port it finds; to force a
specific one:

```bash
ARDUINO_PORT=/dev/tty.usbmodemXXXX npm start
```

Open the Serial Monitor once after uploading to confirm you see `HAND:1` /
`HAND:0` lines toggle when you cover/uncover the sensor, and to sanity
check the calibration values printed at boot.

### 5. Run

```bash
npm start
```

The server:
1. Fetches and caches the CIID May 2026/27 student profiles **once**, at
   startup (`server/profiles.js`) — not on every interaction. If the network
   isn't reachable, it falls back to the committed cache on disk.
2. Opens the Arduino serial connection if one is found.
3. Serves the front-end ritual and a small WebSocket channel that relays
   hand-presence events (real or dev-simulated) to the browser.

## Developer / troubleshooting panel

Hidden by default — press **``` `** or click the dot in the bottom-right
corner. It is intentionally styled like a plain debug console (monospace,
boxed off) so it never reads as part of the ritual.

It shows live status for: server/WebSocket connection, Arduino/photoresistor,
microphone, whether speech was detected, whether a profile was matched, AI
processing, and audio playback — plus manual triggers for every stage of the
state machine (hand on/off, name input, profile selection, question input,
fortune generation, fortune reveal, and a full reset).

## Project layout

```
server/
  index.js      Express + WebSocket server, Arduino bridge, REST API
  profiles.js   Scrapes + caches CIID profiles at startup; fuzzy name matching
  fortune.js    Anthropic API call + offline fallback fortune generator
  tts.js        ElevenLabs voice synthesis (falls back to the browser voice)
  data/
    profiles.cache.json   Seeded cache (overwritten by a fresh scrape at boot)
public/
  index.html    The ritual shell + dev panel markup
  style.css
  js/
    visualizer.js   Canvas orb + particle field, one state per ritual stage
    audio.js        Procedural ambient soundscape (Web Audio API)
    speech.js       TTS ("the oracle's voice") + STT ("the oracle's ear")
    main.js         The state machine that ties it all together
arduino/
  oracle_photoresistor/oracle_photoresistor.ino
```

## Notes on the fortune-telling itself

The oracle is instructed (see the system prompt in `server/fortune.js`) to
never summarize a person's biography back at them. Instead it's asked to
fuse two or three unrelated fragments of what they've already done or love
with the question they just asked, into one short, specific, whimsical,
optimistic, slightly mysterious *possible* future — something that isn't
true yet, but feels unmistakably like them. Structure: recognition → mystery
→ unexpected connection → prediction → a memorable closing line, meant to be
spoken aloud in about 20–40 seconds.
